# ไอเดีย PetID — "ทะเบียนตัวตนสัตว์เลี้ยง" และการต่อเข้ากับระบบสัตว์หาย

สถานะ: เสนอเพื่อตัดสินใจ (D1b) · 2026-10-03

---

## 1. ปัญหา (root cause ไม่ใช่ symptom)

**Symptom:** หมา-แมวจรจัด ~3.6 ล้านตัว · คนถูกสุนัขกัด >1 ล้านคน/ปี · สัตว์หายแล้วหาไม่เจอ

**Root cause ที่ยืนยันได้:** สัตว์เลี้ยงในไทย **ไม่มีตัวตนที่ตรวจสอบได้** — ไม่มีเลขอ้างอิงที่ผูกสัตว์ตัวหนึ่งกับเจ้าของรายหนึ่งแบบที่คนอื่นตรวจสอบได้

กทม. รู้ปัญหานี้ จึงออก **ข้อบัญญัติฯ การควบคุมการเลี้ยงหรือปล่อยสัตว์ พ.ศ. 2567** บังคับ จดทะเบียน + ฝังไมโครชิป (ภายใน 120 วันหลังเกิด / 30 วันหลังรับมาเลี้ยง) เดิมเริ่ม 10 ม.ค. 2569

**แต่ กทม. เลื่อนบังคับใช้ออกไป 1 ปี** — เหตุผลที่ให้คือ *เอกสารซับซ้อน · จุดบริการฝังชิปไม่พร้อม · กลัวคนทิ้งสัตว์เพราะทำตามไม่ได้*

→ **นี่คือช่องว่าง: กฎหมายมี แต่กระบวนการไม่มี** ปัญหาเป็น operational/software ไม่ใช่ legal — ตรงกับสิ่งที่ทีม 4 คนทำได้จริงในเทอมเดียว และเป็นหลักฐานที่สืบย้อนได้ (มี ข่าว + ตัวบทกฎหมาย + ตัวเลขตลาด)

---

## 2. ระบบคืออะไร

**PetID = ทะเบียนตัวตนสัตว์เลี้ยง + คิวบริการฝังชิป/ขึ้นทะเบียน**

| Actor | ทำอะไร |
|---|---|
| Owner (primary) | เพิ่ม pet → ระบบคำนวณ ComplianceDeadline ให้ → จอง slot ที่ ServicePoint → ได้ใบทะเบียน + QR |
| ServicePoint Staff (คลินิก/สำนักงานเขต) | เปิด slot, เรียกคิว, ยิงเลขไมโครชิป 15 หลักเข้าระบบ, ออกทะเบียน |
| ผู้พบเห็นสัตว์ (public, ไม่ต้อง login) | สแกน QR / กรอกเลขชิป → เห็นว่า "สัตว์ตัวนี้มีเจ้าของ" + ส่งข้อความถึงเจ้าของ **โดยไม่เห็นเบอร์/ที่อยู่** |
| เขต/ผู้ดูแล (secondary) | ดูสถิติความครอบคลุมในพื้นที่ |

## 3. จุดที่ยากเชิงวิศวกรรม (= ของที่ demo แล้วได้คะแนน 7.7)

| # | Business rule | บังคับด้วยอะไร | Failure case ที่โชว์ได้บนจอ |
|---|---|---|---|
| R1 | 1 slot จองได้ครั้งเดียว | partial unique index + transaction | 2 คนกดยืนยัน slot เดียวกันพร้อมกัน → คนที่สองเห็น "ช่วงเวลานี้เพิ่งถูกจอง" + เสนอเวลาใกล้เคียง |
| R2 | 1 MicrochipId = 1 Pet ทั้งระบบตลอดกาล | `UNIQUE` บน microchip_id | staff ยิงเลขชิปที่มีอยู่แล้ว → ระบบปฏิเสธ + บอกว่าชิปนี้ผูกกับทะเบียนอื่นแล้ว (กันชิปซ้ำ/สวมสิทธิ์) |
| R3 | ขึ้นทะเบียนได้เฉพาะ pet ที่ตัวเองเป็นเจ้าของ | authorization check | owner A ยิง API ของ pet ของ owner B → 403 ไม่ใช่ 404 ที่หลุดข้อมูล |
| R4 | ไม่เปิดเผยข้อมูลติดต่อเจ้าของต่อสาธารณะ | relay message ผ่านระบบ | public สแกน QR → ส่งข้อความได้ แต่ response ไม่มี phone/address เลย (โชว์ใน network tab ได้) |
| R5 | เตือนก่อนครบกำหนดตามข้อบัญญัติ | Celery beat + RabbitMQ | ปิด worker → จองยังได้ปกติ (ไม่พังเส้นทางหลัก) เปิด worker กลับมา → งานที่ค้างถูกส่งต่อ |

**ประเด็น:** R1 คือ concurrency เดียวกับตัวอย่าง vet booking ของอาจารย์ (เรายังได้ failure case ที่สวยที่สุดอยู่) แต่ R2/R3/R4 เป็นของเราเอง และอธิบายได้ด้วยกฎหมายจริง

## 4. ต่อเข้ากับ "ระบบสัตว์หาย" ได้อย่างไร (ข้อเสนอจริง: ทำรวมกัน)

ระบบสัตว์หายที่ lab ออกแบบไว้ มีรูรั่วใหญ่ที่ lab ไม่แตะ: **ไม่มีการยืนยันตัวสัตว์และตัวเจ้าของ** — ประกาศได้ทุกคน อ้างเป็นเจ้าของได้ทุกคน

PetID อุดรูนั้นพอดี:

```
Pet (มี MicrochipId, มีเจ้าของยืนยันแล้ว)
  └─ แจ้งหาย → LostReport
        ├─ ผู้พบเห็นส่ง Sighting (รูป + ตำแหน่ง + เวลา)   ← FR-04/05 ของ lab
        └─ ผู้พบเห็นสแกนชิป/QR → ระบบจับคู่ตัวตนทันที     ← PetID: ของเราเอง
              └─ ขอรับคืน (Claim) → อนุมัติได้ "รายเดียว"  ← single-winner, ของเราเอง
                    └─ นัดรับคืนที่ ServicePoint (slot)     ← R1 concurrency
```

ได้ทั้ง:
- **เรื่องเล่าเส้นเดียว** ตามที่ spec §5.1 ต้องการ: "สัตว์หาย → มีคนเจอ → ยืนยันตัวตนได้ → กลับบ้าน"
- **Failure case 3 แบบ** (slot ชน, ชิปซ้ำ, claim ซ้อน) จากระบบจริง
- **เหตุผลใช้ RabbitMQ จริง** (แจ้งเตือนเจ้าของ/อาสาสมัครในรัศมี — ไม่ใช่ใส่เพราะต้องมี)
- **Privacy เป็น requirement จริง** ไม่ใช่คำพูดบนสไลด์

## 6. ความเสี่ยงที่ต้องยอมรับ

1. **Scope บานได้ง่าย** — ทะเบียน + คิว + สัตว์หาย + claim + geo = เยอะสำหรับ 4 คน → ต้องตัด (ดู §7)
2. **ไม่มีเครื่องอ่านชิปจริง** — ต้องประกาศเป็น Known Limitation: staff พิมพ์เลข 15 หลักเอง (ยังทดสอบ R2 ได้ครบ)
3. **ข้อบัญญัติถูกเลื่อน** — ต้องพูดเองบนสไลด์ว่ารู้ และอธิบายว่าการเลื่อนคือเหตุผลที่ระบบนี้จำเป็น ไม่ใช่เหตุผลที่ไม่ต้องทำ

## 7. ขอบเขตที่แนะนำให้ "ตัด" ตั้งแต่ต้น

ตัดออก: ชำระเงิน · แผนที่ geo-radius แบบ PostGIS · AI/LLM จับคู่รูป · Kubernetes · mobile app (ใช้ responsive web) · อาสาสมัครในรัศมี (ถ้าเวลาไม่พอ)

เหลือแกน: ทะเบียน+ชิป (R2,R3) · จอง slot (R1) · แจ้งหาย+เบาะแส · claim รายเดียว · relay ข้อความ (R4) · reminder (R5)
